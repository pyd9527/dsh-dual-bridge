# 换机与升级排查手册

> 适用对象：已经装过或准备装 `dsh-dual-bridge`（双向沟通桥）的人。
> 解决的问题：**换了电脑、升了插件版本之后，工具为什么不出现 / 为什么还在跑旧代码 / 通道断了怎么恢复 / 怎么证明没把原有双向沟通弄坏**。
> 手册里所有具体 id（deviceId / sessionId / workspaceId / 身份目录 hash）都写成 `<见本机配置>`，用 `dual_status`、`dual_peers`、`dual_workspaces`、`dual_sessions` 现场读。

## 一、症状速查表

按「你看到的现象」查。每条给**一个动作**，做完看「期望结果」那一栏对不对得上。

| 症状 | 最可能原因 | 一条命令 / 一个动作 | 期望结果 |
| --- | --- | --- | --- |
| 模型侧**完全看不到 `dual_*` 工具** | 包没进 profile，或装了但没加载 | `node install.mjs --check`（退出码 `2` 就是缺项）→ 缺就 `node install.mjs`；本会话里也可以让 Agent 用 `plugin_manager` `install_bundle` | 工具列表里出现 6 个 `dual_*`；`dual_status` 能调用 |
| 工具出现了，但**输出是旧版本**（没有「运行时来源」「插件版本」行） | 桌面端进程里缓存的是**旧模块** —— ESM 模块缓存不随文件改动失效 | **完全退出 DSH Desktop 再打开**（toggle / 重装 / 换包路径 / 换入口文件名四种做法都无效，已实测） | `dual_status` 输出里出现「运行时来源 : …」与「插件版本 : 0.2.2」两行 |
| `RPC harness.remote.call timed out after 60000ms` | 宿主 `dshRemoteClient` 缓存的连接早已死掉，但 `ensureConnected()` 只看 deviceId 匹配就把它返回 | 0.2.1 起会自动探活 + 丢缓存重连，**通常重试就过**；频繁复现就把 `runtimeMode` 设成 `own` | 下一次调用在几秒内返回；不再干等 60 秒 |
| `The authenticated Noise channel is not connected.` | 同上：P2P 通道静默掉线，`client.closed === false` 但握手已断 | 同上（0.2.1 自动重连并重试一次）；持续复现设 `runtimeMode: own` | 重试成功，调用返回 |
| `BRIDGE_CHANNEL_DEAD` | 连上了对端，但**发不出请求**：探活连续失败，且已无法整体回退 | 让对端在 Remote 面板**重新登录一次**后重试；或本机改 `runtimeMode: own`（自建运行时 = 全新连接） | 调用成功返回 |
| `BRIDGE_NO_HOST_RUNTIME` | 配了 `runtimeMode: host`，但宿主身份未就绪 / `ds-harness-remote` 没加载 | 把 `runtimeMode` 改回 `auto`（或 `own`） | 调用成功，`dual_status` 的「运行时来源」显示 auto 或 own |
| `BRIDGE_PEER_OFFLINE` | 指定的对端当前不在线 | `dual_peers` 看谁在线；或让对端把 DSH 开着并登录**同一账号** | `dual_peers` 里该对端变成 `● 在线` |
| `BRIDGE_TRANSPORT_MISSING` | 找不到 `ds-harness-remote` 插件本体（传输层缺失） | `node install.mjs`（会自动补装 `ds-harness-remote@0.5.7`）；或 `dsh plugin --profile desktop add ds-harness-remote` | 报错消失；`node install.mjs --check` 退出码 `0` |
| **对端 UI 侧栏看不到新建的会话** | 建成了**游离会话**（没挂到对端任何工作区） | 保持 `autoWorkspace: true`（默认就是 true），或调用时显式传 `workspace` | 新会话出现在对端 UI 侧栏，且挂在对端某个工作区下 |
| `install_bundle` 报 `ambiguous-install` | pnpm 一次改了不止一个依赖项，管理器无法判定「这次装的是哪个包」 | 改用命令行装：`node install.mjs` 或 `dsh plugin --profile desktop add "<包目录绝对路径>"` | 安装返回 `applied`，工具出现 |
| 安装报 `EPERM` / `permission denied` | 文件被占用（DSH Desktop 正在跑）或权限不足 | **完全退出 DSH Desktop** 后再用命令行装（`node install.mjs`） | 安装成功，重开桌面端后工具可用 |
| 对端上游返回 400「conversation id missing」 | 那条远端会话的 id 在对端已经不存在（会话被删 / 换了机器 / 会话没 attach 到工作区） | `dual_sessions` 列对端现存会话；`dual_inbox` 看有没有历史；确认后在 `dual_send` 里**换一条会话**（或给 `workspace` 让它新建一条） | 调用成功返回对端回复 |

> **关于最后一行**：该报错的**具体复现路径本机未实测**（未在本机触发过这个上游 400）。上面给的是按「会话 id 语义」推导的处置方向；如果你遇到的是别的 400 文案，按 `dual_sessions` 列出的真实会话 id 为准。

### 两条最容易误判的事

- **`cordis.patch.yml` 里 grep 不到 `dual` ≠ 没装上。** 插件包的 patch 是**运行时合成**的，不会回写到 profile 的 `cordis.patch.yml`。判断装没装要看工具列表 / `dual_status`，不要看那个文件。
- **`plugin_manager` 的 `set_plugin` 目标不是包名。** 要传的是 Loader 条目 id **`include:dual-bridge`**；传包名 `dsh-dual-bridge` 会报 `unknown-plugin`。

## 二、为什么「改了插件代码」不生效

这是本插件最容易踩的坑：**明明文件改了，`dual_status` 还是旧输出**。原因是桌面端进程里的 **ESM 模块缓存不会因为文件变化而失效**。

### 2.1 三条源码依据

| 依据 | 位置 | 原文要点 |
| --- | --- | --- |
| ① 重载函数在 hmr 缺失时**直接返回空数组** | `@deepseek-ai/dsh-plugin-manager\lib\index.js:2035-2038` | `async reload(requiredIds = []) { if (this.ownerContext.get("hmr") === void 0) return []; return reconcileProfilePatches(...) }` —— 没有 hmr 服务就**什么也不重载**，不是失败、是静默跳过 |
| ② 桌面端启动时 **hmr 的模块根为空** | `@deepseek-ai/dsh-base\cordis.patch.yml:27-32` | hmr 条目写着注释「Profile configuration reloads by default; module roots are opt-in.」，配置为 `config: { root: [] }`，并按 `disabled: !!js "!ctx.get('profileContext')"` 条件启用 |
| ③ 模块级 HMR 需要 `--expose-internals` **且** root 非空 | `@deepseek-ai/dsh-hmr\lib\index.js:317` | `if (!this.ctx.loader.internal && config.root.length > 0) throw new Error("--expose-internals is required for module HMR")` —— 两个条件缺一不可 |

一句话结论：

- **profile 的「配置重载」默认是开着的**（改 `cordis.patch.yml` 里的配置会生效）；
- **「模块 HMR」（代码级热替换）默认是关着的**（`root: []`，且桌面端不带 `--expose-internals`）；
- 所以 `plugin_manager` 的 `install_bundle` 返回 `application: 'applied'`，走的是**配置层**的热加载 —— 它能把**新插件**挂上（首次安装确实即装即用），但**换不掉已经加载进内存的旧模块**。源码里同一个开关也管着这句话：`index.js:2046` 的 `application: this.ownerContext.get("hmr") !== void 0 ? "applied" : "restart-required"`。

### 2.2 四种「看起来该有用」的做法，全部实测无效

以下四种做法都**不能让新代码生效**（已实测，`dual_status` 始终返回旧输出）：

1. **toggle 插件**（`plugin_manager` `set_plugin` 把 `include:dual-bridge` 关掉再打开）；
2. **重装**（`install_bundle` 再装一次同一个包）；
3. **换包路径**（把包放到别的目录再装）；
4. **换入口文件名**（`package.json` 的 `exports` 指向 `impl.js` / `impl-0.1.2.js` 这类新文件名）。

原因一致：这些动作改变的是**磁盘上的文件与配置**，而进程内存里那份模块引用没被动过；`reload()` 又因为 hmr 缺失直接返回 `[]`。

### 2.3 正解 A：完全退出 DSH Desktop 再打开（**已实测有效**）

```
1. 完全退出 DSH Desktop（不是最小化、不是关窗口 —— 进程要真的退出）
2. 重新启动 DSH Desktop
3. 跑 dual_status，确认输出里有「运行时来源」与「插件版本 : 0.2.2」两行
```

**判断跑的是不是新代码**，只看这两行：

```
运行时来源 : auto
插件版本   : 0.2.2
```

**这两行只要缺一行，你跑的就是旧代码。** 这是唯一可靠的判据 —— 别靠「文件时间戳变了」「重装成功了」来判断。

> 首次安装是例外：`install_bundle` 返回 `application: 'applied'` 时工具**确实已经热加载**，可以立即使用，不需要重启。只有**改过插件自身代码之后**才必须完全退出重开。

### 2.4 正解 B：把插件代码放进 hmr 的模块观察路径（**未实测，属推测**）

理论上让模块 HMR 生效需要同时满足三件事：

1. 桌面端以 **`--expose-internals`** 启动（否则 `dsh-hmr\lib\index.js:317` 直接抛错）；
2. hmr 的 `config.root` **非空**（现在是 `root: []`），指向你放插件源码的目录；
3. 该目录**不落在** hmr 的默认忽略集里（`dsh-hmr\lib\index.js:240-245` 默认忽略 `**/node_modules`、`**/.*`、`cache`、`data`）。

**以上全部未实测**：本机没有验证过在桌面端传 `--expose-internals`、也没有验证过 root 非空后代码改动是否真的被重载。此处只作为方向记录，**不要当成可用方案照做**；要试请先备份 profile，并在试完后跑一遍第四节的护栏三件套。

## 三、验收清单（从零到可用，逐条勾）

每一条都给了可复制的命令或工具调用。**前 7 条是「装好了」，后 5 条是「没弄坏东西」。**

- [ ] **1. 包在位** —— 目录里应有 `index.js`、`package.json`、`cordis.patch.yml`、`install.mjs`、`locale\`、`icon.svg`、`README.md`：
  ```powershell
  Get-ChildItem "D:\plugins\dsh-dual-bridge" | Select-Object Name, Length
  ```
- [ ] **2. 体检通过** —— `install.mjs --check` 退出码语义：`0` = profile / 通道 / 身份 / `dsh` CLI 全部就位；`2` = 有缺项或找不到 `dsh` CLI；`1` = 某条命令执行失败：
  ```powershell
  cd "D:\plugins\dsh-dual-bridge"; node install.mjs --check; $LASTEXITCODE
  ```
- [ ] **3. 装进 profile**（体检报缺时才需要）：
  ```powershell
  cd "D:\plugins\dsh-dual-bridge"; node install.mjs
  # 或者：dsh plugin --profile desktop add "D:\plugins\dsh-dual-bridge"
  ```
- [ ] **4. profile 已登记** —— `dependencies` 里有 `dsh-dual-bridge`，`dsh.profile.bundles` 里也有它：
  ```powershell
  Select-String -Path "$env:USERPROFILE\.dsh\profiles\desktop\package.json" -Pattern 'dsh-dual-bridge'
  ```
- [ ] **5. 工具已注册** —— 让模型调用 `dual_status`（无参数）。也可以查运行时工具表：`cordis_inspect_query`（host / Tool / `listTools`）应含 6 个 `dual_*`。
- [ ] **6. 跑的是新代码** —— `dual_status` 输出**必须**含这两行（缺一行就是旧代码，回 2.3 完全退出重开）：
  ```
  运行时来源 : auto
  插件版本   : 0.2.2
  ```
- [ ] **7. 默认配置正确** —— `dual_status` 的「【默认配置】」块里能看到 `autoWorkspace` 那一行，且是「开（新建会话自动挂对端最近更新的工作区，对端 UI 侧栏可见）」。
- [ ] **8. 对端在线** —— `dual_peers`（无参数）应至少有一台 `● 在线`；名称按你的实际设备名（见本机配置）。
- [ ] **9. 能列对端工作区** —— `dual_workspaces`，`peer` 传你的对端名（见本机配置）。期望拿到 `workspaceId` / `path` / `title` / session 数。
- [ ] **10. 护栏：CRITICAL 干净** —— 装插件不该动传输层本体与身份文件：
  ```powershell
  pwsh -NoProfile -File "D:\plugins\verify\check.ps1" -Compact
  ```
  期望**退出码 `0`**，且 `CRITICAL CHANGED = 0`、`IDENTITY CHANGED = 0`。
  （若只有 profile 的两个配置文件变了、且确实是你刚装的插件造成，加 `-ProfileConfigIsExpected` 复核 —— 它只把 PROFILE 项降级为 INFO，**不会放过 CRITICAL / IDENTITY**。）
- [ ] **11. 护栏：原有双向沟通仍可用** —— 非破坏性回归，只跑 `--list` 与 `--workspaces` 两条**只读**路径：
  ```powershell
  pwsh -NoProfile -File "D:\plugins\verify\regression.ps1"
  ```
  期望**退出码 `0`**、两步均 `PASS`（`--list` 拿到 `hosts`、`--workspaces` 拿到 `workspaces`）。
  退出码 `2` = `OFFLINE`（通道本身健康、只是对端离线，等对端上线复跑）；退出码 `1` = `BROKEN`（看日志里的 stderr 原文，走第四节处置）。
- [ ] **12. 回滚预案演练过一遍**（只预览、绝不写盘）：
  ```powershell
  pwsh -NoProfile -File "D:\plugins\verify\rollback.ps1" -WhatIf
  ```

**12 条全勾 = 从零到可用，且证明没把原有双向沟通弄坏。**

## 四、护栏与回滚

`verify\` 目录存在的意义，就是把「装插件的过程不会让现有双向沟通报废」这句话变成**可执行、可复现、有退出码的证据**。

### 4.1 四个脚本各管什么

| 脚本 | 作用 | 常用命令 |
| --- | --- | --- |
| `baseline.ps1` | **采基线**（时间点快照）：传输层插件本体逐文件 SHA256 + treeHash、驱动脚本、身份文件、profile 配置 | `pwsh -NoProfile -File verify\baseline.ps1` |
| `check.ps1` | **逐项核对**当前状态与基线 | `... verify\check.ps1 -Compact`；对照旧基线加 `-BaselinePath verify\baseline.pre-install.json`；预期变更加 `-ProfileConfigIsExpected` |
| `regression.ps1` | **非破坏性回归**：只跑 `--list` / `--workspaces` 两条只读路径 | `... verify\regression.ps1` |
| `rollback.ps1` | **一键回滚 profile 配置**（先备份再恢复，恢复后自动跑 `check.ps1` 核对） | `... verify\rollback.ps1 -WhatIf`（预览）/ 去掉 `-WhatIf`（实际执行） |

### 4.2 判读口径

| 级别 | 覆盖对象 | 计不计入退出码 |
| --- | --- | --- |
| **CRITICAL** | `ds-harness-remote\`（914 个文件 + treeHash）、`dsh-remote-task.mjs` | **一律计入**，任何开关都不能降级 —— 这是「现有双向沟通被改动」的硬证据 |
| **IDENTITY** | host / client 身份文件（存在性 + 字节长度） | 消失 / 长度变化计入；同长度换 hash 只 WARN |
| **NON-CRITICAL** | profile 的两个配置文件 | 默认计入；`-ProfileConfigIsExpected` 可降级为 INFO（`dsh plugin add` 本来就会重写它们） |

**「装了插件之后算健康」的三条判据（全满足才算）**：

1. `check.ps1 -Compact` **退出码 `0`**（或差异只落在 profile 两项且已用 `-ProfileConfigIsExpected` 复核）；
2. `regression.ps1` **退出码 `0`**、`PASS` / `PASS`；
3. `CRITICAL CHANGED = 0` **且** `IDENTITY CHANGED = 0`。

### 4.3 `rollback.ps1` 的边界（重要）

`rollback.ps1` **只恢复 profile 的 `package.json` 与 `cordis.patch.yml`** 两个文件（恢复前先备份）。

**它不覆盖 `ds-harness-remote` 本体**（CRITICAL 级）。也就是说：

- 如果 `check.ps1` 报 **CRITICAL CHANGED > 0** —— 传输层本体或驱动脚本被改过 —— **文件级回滚救不了它**，正确修法是**重装插件**：
  ```powershell
  dsh plugin --profile desktop add ds-harness-remote@0.5.7
  # 或直接让装机脚本补装：node install.mjs
  ```
- 它也不碰 `dsh-dual-bridge\` 自身 —— 插件自己的问题请改代码 / 重装本插件，不要指望回滚。

**处置顺序**：① 停手，别继续改传输层本体 → ② 若是 profile 配置被动过 → `rollback.ps1`（先 `-WhatIf`）→ ③ 若是传输层本体被动过 → 重装 `ds-harness-remote` → ④ 复跑 `regression.ps1` 确认通道仍可用。

### 4.4 护栏的覆盖边界（别过度解读）

- 护栏只能证明「**与上次 `baseline.ps1` 相比未变**」，不能证明「从未变过」；
- 回归只覆盖 `--list` / `--workspaces` 两条**只读**路径，**不覆盖** UI 渲染、会话创建、消息投递这些写路径 —— 那部分要靠真工具调用验证（`dual_send` 往返、`dual_inbox` 只读、`dual_workspaces` 列举）。

## 五、第二台 / 第三台电脑

### 5.1 配对的前提

- **两台机器必须用同一个 DeepSeek 账号登录 Remote 面板**（同一个 relay，默认 `https://dsh.r2049.cn`）。**配对是按账号配的，不是按 deviceId。**
- **重装之后 deviceId 会变，这是正常的** —— 不要因为 deviceId 变了就以为配对断了；只要还是同一账号登录同一 relay，对端会重新出现在 `dual_peers` 里。
- 通道默认走 P2P，打不通会自动降级走 relay。

### 5.2 身份文件在哪

```
$DSH_HOME\remote\servers\<hash>\host\   device.json / device.key / server-credentials.json / trusted-peers.json
$DSH_HOME\remote\servers\<hash>\client\ device.json / device.key / server-credentials.json / trusted-peers.json
```

- `$DSH_HOME` 默认是 `C:\Users\<你>\.dsh`（`dsh-dual-bridge` 的代码取 `DSH_HOME` 环境变量，没有就用家目录下的 `.dsh`）；
- `<hash>` 是本机配置里的一个目录名 —— **不要猜、不要照抄别人的**，去 `$DSH_HOME\remote\servers\` 下看实际有哪些目录。

### 5.3 换机时怎么带身份

**原则：能整目录带就带，带不了就重新登录（会生成新身份）。**

| 做法 | 操作 | 结果 |
| --- | --- | --- |
| **A. 带过去（推荐）** | 把 `$DSH_HOME\remote\servers\<hash>\` **整个目录**复制到新机器的同名位置（保持 `host\` / `client\` 子目录结构） | 身份不变，deviceId 不变；新机器直接以同一身份上线 |
| **B. 不带，重登** | 新机器上装好插件、打开 DSH、在 Remote 面板用**同一账号**登录 | 自动生成新的 `device.json` / `device.key`，**deviceId 会变** —— 正常；对端按账号仍能发现你 |

**带身份的注意点**：

- `device.key` 与 `server-credentials.json` 是**凭据**，按本机惯例存进凭据库、不要贴进聊天或文档（记忆文件也不要写明文）；
- 复制后**不要手工改文件内容** —— 手工改长度会让护栏的 IDENTITY 检查报 CHANGED；
- 复制目录时**不要带上 `node_modules`**（那是插件本体，属于要单独重装的东西）。

### 5.4 加第三台机器的顺序

1. **每台机器各装一次本插件**：`node install.mjs`（体检 → 找 `dsh` CLI → 缺 `ds-harness-remote@0.5.7` 就自动补装 → 装本插件）；
2. **每台机器用同一账号登录同一 relay**；
3. **互相确认**：在任意一台上跑 `dual_peers`，应能看到另外两台 `● 在线`；跑 `dual_status`，确认「运行时来源」「插件版本 : 0.2.2」两行都在；
4. **给每台机器配一个默认对端**（`defaultPeer`）与**固定会话**（`defaultSession`），跨机派活时用 `dual_send`，消息开头写方向标记（如 `【A→B】…`），这样对端 UI 里一眼能看出是谁发的；
5. **跑一遍护栏**（第四节三条判据），确认三台机器上原有双向沟通都还正常。

### 5.5 迁移检查清单

- [ ] 身份目录存在：`$DSH_HOME\remote\servers\<hash>\` 下 `host\` 与 `client\` 各 4 个文件（`device.json` / `device.key` / `server-credentials.json` / `trusted-peers.json`）；
- [ ] `node install.mjs --check` 退出码 `0`（profile / 通道 / 身份 / CLI 齐全）；
- [ ] 桌面端已完全重启过一次（确保跑的是新代码），`dual_status` 两行判据都在；
- [ ] `dual_peers` 能看到对端且 `● 在线`；
- [ ] 原驱动脚本仍可用：`node dsh-remote-task.mjs --list` 仍返回 `hosts` 数组；
- [ ] `verify\check.ps1 -Compact` 退出码 `0`，`CRITICAL CHANGED = 0`、`IDENTITY CHANGED = 0`；
- [ ] `verify\regression.ps1` 退出码 `0`、`PASS` / `PASS`。
