# 新电脑装机与团队组建手册

面向「换电脑 / 换 DSH 版本 / 新加一台电脑」的落地手册。目标：装插件 + 简单设置就能打通跨机双向沟通，并能按团队形态分工。

本手册涉及的所有机器 id、会话 id、工作区 id 一律写成 `<见本机配置>` 或占位符 —— 真实值不写进文档，用时从本机配置读取。

---

## 0. 前置条件

每台要参与跨机沟通的机器需要满足：

1. 已装 DSH（Desktop 版）。
2. `ds-harness-remote` 插件已装并已登录（本桥复用它的身份与 relay，不自带账号体系）。**没装也行** —— 第 1 节的 `install.mjs` 会检测到并自动补装 `ds-harness-remote@0.5.7`。
3. 已装 `dsh-dual-bridge` 插件（本手册第 1 节）。
4. 能访问 relay 服务 `https://dsh.r2049.cn`。

> 两台机器的 DSH 版本**不要求完全一致**。本桥用到的符号只有 `ClientModeRuntime` / `ClientServerApi` / `IdentityStore` / `ServerCredentialStore` / `resolveConfig` / `serverStorageDirectory` / `RemoteTypertGateway`，全部在 `ds-harness-remote@0.5.7` 的导出表里（47 个导出之一），**不会缺**。真正会随版本变的是**远端端点形状**，插件已用形状自适应调用兜住：`invoke` 先试 `args:{request}`，报 `missing "_request"` / `unexpected "request"` 自动改 `{_request}`，再报反向错误就改平铺。若对端版本确实没有某个端点，远端会返回 `gateway/invocation-unavailable`（而不是形状错），插件把它当 fatal 报出 —— 换用 `dual_peers` / `dual_sessions` 等基础工具，或升级对端即可。

## 1. 三步装机流程（每台机器各做一遍）

### 第 1 步：放包 + 装插件

**新电脑上首选单文件脚本 `bootstrap.mjs`：只拷一个文件，不需要先放整包。**

```powershell
# 只把 bootstrap.mjs 拷到新机器任意位置，然后：
node bootstrap.mjs                 # 物化插件 → 体检 → 找 dsh CLI → 缺通道补装 → 装本插件
node bootstrap.mjs --check         # 只体检（不写盘、不安装）
node bootstrap.mjs --profile web   # 装进其它 profile（默认 desktop）
node bootstrap.mjs --dir <目录>    # 指定物化位置（默认 <当前目录>\dsh-dual-bridge）
node bootstrap.mjs --no-transport  # 不自动补装通道
```

它把整包 8 个文件以 base64 内联在自己身上，**已实测物化结果与源包逐字节一致**（8/8 文件 SHA256 相同）。做完四件事：**① 物化插件包 → ② 体检 → ③ 找 `dsh` CLI → ④ 缺 `ds-harness-remote` 就自动补装、再装本插件**。

`--check` 退出码：`0` = profile / 通道 / 身份 / dsh CLI 四项齐全；`2` = 有缺项或找不到 CLI；`1` = 安装命令失败。**身份缺失不算失败**（新机器本来就是装完才登录）。

---

**已有整包目录时，用包内自带的 `install.mjs`**（等价能力）：

```powershell
cd "<放好的包目录>\dsh-dual-bridge"
node install.mjs --check   # 只体检：profile 目录 / ds-harness-remote / 本机身份 / dsh CLI（退出码 0=正常，2=有问题）
node install.mjs           # 体检 + 缺通道就自动补装 + 装本插件
node install.mjs --profile web   # 装进其它 profile（默认 desktop）
node install.mjs --no-transport  # 不自动补装通道
node install.mjs --dir <目录>    # 显式指定插件目录（默认脚本所在目录）
```

它按顺序做四件事：**① 体检 → ② 找 `dsh` CLI（PATH → `%APPDATA%\DSH Desktop\host-commands\<profile>\generations\<hash>\bin\dsh.cmd`）→ ③ profile 里缺 `ds-harness-remote` 就自动补装 `ds-harness-remote@0.5.7` → ④ 装本插件**。第 ③ 步是关键：**新机器不必再自己先装通道**，一条命令把「通道 + 本插件」都装好。它不写任何 profile 文件、不改 `ds-harness-remote` 本体、不碰身份目录。装完后 `package.json` 声明的 `bin` 也让它可以被 `dsh-dual-bridge-install` / `dsh-dual-bridge-bootstrap` 直接调用。

> 两个脚本都用 `quoteWin()` 自拼带引号的命令行：`dsh` CLI 路径含空格（`...\DSH Desktop\...`），Windows 下 `shell: true` 不会替你给 argv 加引号，直接传会报 `'C:\Users\USER\AppData\Roaming\DSH' is not recognized`。

脚本结束时按保守做法提示**完全退出 DSH Desktop 再打开**（命令行装包属冷装，不保证热加载）；想省这一步就先试 `dual_status`，工具在就不用重开。

**命令行（不受 UI 独占影响）**

```powershell
dsh plugin --profile desktop add "D:\plugins\dsh-dual-bridge"
```

- 用**绝对路径**，含空格必须加引号。
- 换 DSH 版本后 `dsh` 命令路径会变（它指向 `%APPDATA%\DSH Desktop\host-commands\<profile>\generations\<hash>\bin\dsh.cmd`），**开一个新终端**再跑，让 PATH 重新解析。
- 公司机（DSH 装在 `D:\AZ\DSH Desktop`）用这条命令最稳：图形界面的安装操作可能被正在运行的实例占住 profile 目录。
- 这条路径**不会**自动补装通道；若 profile 里没有 `ds-harness-remote`，先 `dsh plugin --profile desktop add ds-harness-remote@0.5.7`。

**会话内安装**

让模型调用 `plugin_manager`，`action = "install_bundle"`，`target` 填包目录绝对路径。若返回 `pendingBuilds`，明确同意后再传 `approvedBuilds`。同样**不自动补装通道**，通道缺失时先按上一行手工补。

> 本机当前是 `link:E:/DeepSeek Harness/测试/dsh-dual-bridge`（pnpm link），`node_modules\dsh-dual-bridge` 是指向工作区的符号链接。**换电脑时把整个 `dsh-dual-bridge` 目录拷过去**，再对新目录的绝对路径跑上面的安装命令。

### 第 2 步：两台机用同一个 DeepSeek 账号登录 Remote

在每台机器的 DSH 里打开 **Remote 面板**，用**同一个 DeepSeek 账号**登录。

登录后本机获得 client 身份，对端会出现在本机设备目录中，本桥的工具才能按名称/deviceId 找到对端。

### 第 3 步：验证（装完即用，不需要重启）

实测：`install_bundle` 返回 `application: "applied"` 时，Host 已经**热加载**并注册了 6 个工具（`cordis_inspect_query` 的 host / `listTools` 能直接看到）。

**装机自检**（让模型执行，或自己在会话里问）：

| 检查项 | 期望 |
| --- | --- |
| `dual_status` | 能看到本机 deviceName / deviceId、relay 连接状态、**运行时来源**与**插件版本** |
| `dual_peers` | 能看到对端，且标为 `在线` |
| `dual_workspaces`（对端） | 能列出对端工作区 |
| `dual_sessions`（对端） | 能列出对端会话 |

四项都通过 = 装机完成。

> ⚠ **例外：改过插件自身的代码之后，必须完全退出 DSH Desktop 再打开。**
> 首次安装（`install_bundle` 返回 `application: "applied"`）是热加载、装完即用；但**装完之后再改插件代码，运行中的 Host 不会重新加载** —— 实测改内容后 toggle 插件不生效、换入口文件名不生效、连改 `package.json` 的 `exports` 也不生效，`dual_status` 始终返回旧版输出（Host 的 ESM 模块缓存不会被清掉）。用新进程 `import()` 同一个文件则新版立刻生效。
> **判断方法**：`dual_status` 输出里应有「运行时来源 : …」与「插件版本 : 0.2.2」两行；**没有这两行就是在跑旧代码**。命令行 / `install.mjs` 安装属冷装，也按这一条重开最稳。

**若工具没出现**，再完全退出 DSH Desktop（确认进程真的退出，含托盘与后台进程）重新打开一次。

**一个容易误判的现象**：profile 的 `cordis.patch.yml` 里**看不到** `dual-bridge` 这条 row —— 这是正常的，bundle patch 是运行时合成、不写回 profile 文件。以「6 个工具在不在」为准，不要以文件里有没有那一行为准。

**装机后的首次跑通参考**（v0.2.2 实测）：

- `dual_workspaces` 能列出对端 4 个工作区（双向沟通 / 记忆中枢 / 日常工作 / default-workspace）；
- `dual_send` 复用固定会话，对端回一句短话，单次约 7 秒；
- 什么都不配时 `autoWorkspace` 会把新会话挂到对端「最近更新」的工作区，对端 UI 侧栏可见。

> 说明：`plugin_manager` 的 `set_plugin` 若要按名操作插件，target 用 Loader entry id **`include:dual-bridge`**，不是包名 `dsh-dual-bridge`（填包名会报 `unknown-plugin`）。

## 2. 两台机同账号配对原理

**核心：插件按「账号」配对，不按 deviceId。**

- 每台机器首次登录 Remote 时，`ds-harness-remote` 在身份目录里生成一份**本机身份**（deviceId + 密钥对），并把这份身份绑定到登录的 DeepSeek 账号。
- relay 服务按账号维护一份设备目录：同一账号下登录过的所有设备互相可见。
- 因此**配对动作就是「两边登同一个账号」**，不需要在两端互填 deviceId、不需要交换密钥文件、不需要手工授权对方。
- 换电脑 = 新机器登同一个账号 → 自动出现在其它机器的设备目录里。
- 重装 / 重置身份 = deviceId 会变（新生成的），但账号不变 → 配对关系不受影响。所以配置里**优先用名称匹配**，deviceId 只作为可选加速。

身份目录（两台机器结构相同，`<serverHash>` 由 relay 地址推导，实际值见本机配置）：

```
<DSH_HOME>\.dsh\remote\servers\<serverHash>\
  host\   device.json  device.key  server-credentials.json  trusted-peers.json
  client\ device.json  device.key  server-credentials.json  trusted-peers.json
```

- `client\` = 本机作为「发起方」的身份（本桥用的是这一份）。
- `host\` = 本机作为「被连方」的身份（对端来连你时用）。
- 迁移时要保留整个 `servers\<serverHash>\` 目录，两个子目录都要在。

> 说明：relay 用 WebRTC/P2P 直连，打不通时自动降级到 relay 中转。同一局域网通常走 P2P，跨网走 relay；两条路都不通时对端会显示 `离线`。

### 2.1 通道自愈（0.2.1 起，装机后必读）

**为什么专门讲**：两台机之间的 P2P 通道会**静默失效** —— 进程还活着、`client.closed` 还是 `false`，但对端的 Noise 握手其实早断了。表现是：

- 第一次调用直接报 `The authenticated Noise channel is not connected.`；或
- 什么都不报，一路干等到 **60 秒**才抛 `RPC harness.remote.call timed out after 60000ms`。

两种都不是配置错，**重连一次就能恢复**。原脚本 `dsh-remote-task.mjs` 从不出这问题，因为它每次都是新进程、每次重新建连；插件是长驻进程，连接被缓存复用，所以必须自己处理。

**插件自动做的三层防护**（不用配）：

| 层 | 做什么 | 效果 |
| --- | --- | --- |
| ① 取连接前探活 | 先发一个最便宜的**只读**调用（`session/list`），超时由 `probeTimeoutMs`（默认 4000ms）控制 | 失效通道 **4 秒判死**，不等 60 秒 |
| ② 缓存连接也探活 | `client.closed` 为 `false` **不等于** Noise 握手还在；探测不过就丢缓存、重新建连 | 死连接不会被一直喂给后续调用 |
| ③ 命中可恢复错误就重连重试 | 命中 `Noise channel is not connected` / `RPC … timed out after` / `remote/disconnected` / `socket hang up` / `ECONNRESET` 时，丢缓存、强制重连，把这次调用整体重试一次 | 多数情况重试即好，用户侧无感 |

**⚠ 一条边界（避免误以为任何失败都会自动重试）**：`dual_send` 只在**「定会话 + 选模型」阶段**自愈；**「起流 + 下发消息」那一段失败就如实报错、不自动重试** —— prompt 一旦被对端接受，重试会把**同一条消息发第二遍**。所以发消息失败时，先用 `dual_inbox` 看对端收没收到，再决定要不要重发。

**想最稳**：把 `runtimeMode` 设成 `own`，每次调用都自建运行时、每次重新建连，完全不碰宿主那条可能已死的缓存连接。

## 3. 配置示例

在 profile 的 bundle patch（`cordis.patch.yml`）里 `dsh-dual-bridge` 这条 entry 的 `config` 下配置。**10 个键，全部可选，都有默认值**：`serverUrl`、`defaultPeer`、`defaultWorkspace`、`defaultSession`、`defaultModel`、`timeoutMs`、`connectMode`、`autoWorkspace`、`runtimeMode`、`probeTimeoutMs`（键的完整含义见 `dsh-dual-bridge\README.md` 第二节）。

**YAML（`cordis.patch.yml` 里的行 config）**

```yaml
- id: dual-bridge
  name: dsh-dual-bridge
  config:
    serverUrl: https://dsh.r2049.cn
    defaultPeer: 公司机            # 值须等于 dual_peers 列出的对端名称或 deviceId
    defaultWorkspace: <见本机配置>
    defaultSession: <见本机配置>
    timeoutMs: 600000
    connectMode: reuse
    autoWorkspace: true            # 开着才能保证新会话在对端 UI 侧栏可见
    runtimeMode: auto
    probeTimeoutMs: 4000           # 通道探活超时；0.2.1 起通道自愈靠它判死失效连接
```

**JSON（等价写法）**

```json
{
  "serverUrl": "https://dsh.r2049.cn",
  "defaultPeer": "公司机",
  "defaultWorkspace": "<见本机配置>",
  "defaultSession": "<见本机配置>",
  "timeoutMs": 600000,
  "connectMode": "reuse",
  "autoWorkspace": true,
  "runtimeMode": "auto",
  "probeTimeoutMs": 4000
}
```

**三个「行为类」键怎么选**（跨机最常调的三个）：

| 键 | 什么时候改 | 改成什么 |
| --- | --- | --- |
| `runtimeMode` | 宿主那条连接不可靠、想让每次调用都重新建连（最稳） | `own` |
| `probeTimeoutMs` | 网络差、探活被误判成失效 | 调到 `8000`~`10000` |
| `autoWorkspace` | 不想让插件自动挂工作区（会得到对端 UI 看不见的游离会话） | 一般**不要**关 |

**关于对端别名**：本插件**没有**别名表机制 —— `defaultPeer` 与调用时的 `peer` 参数都必须写成对端的**真实名称**（即 `dual_peers` 列出来的名字）或它的 deviceId。上面示例里的 `公司机` / `私人机` 是给人看的叫法，实际填的时候照抄 `dual_peers` 的输出即可；填错会报 `BRIDGE_PEER_NOT_FOUND`，报错信息里会把已知对端列出来。

**多对端时**：配置项只提供**一个**默认对端（`defaultPeer`），但 `dual_send` / `dual_workspaces` / `dual_sessions` / `dual_inbox` 都接受 `peer` 参数（名称或 deviceId）。所以三台以上时：

- 在配置里设**最常用的那台**为 `defaultPeer`；
- 其余对端在调用时用 `peer` 参数按名称指定，不必写进配置。

**两端配置不对称是正常的**：

- 在私人机上，`defaultPeer` 填公司机的名称；
- 在公司机上，`defaultPeer` 填私人机的名称。
- 名称只在本机生效，不需要两端名字一致（建议还是取一致的名字，便于人和模型都记得住）。

> `defaultModel` / `model` 参数的写法：**必须是 `provider/model`**（含 `/`）。不含 `/` 的值会被忽略、回落到插件默认值 `workbuddy-xdpool-global/deepseek-v4.1-flash`。拿不准就留空，让对端用它自己的默认模型。

## 4. 团队组建

思路借鉴 `ds-bot` 的团队形态：**一个 Main Bot 统筹 + 若干成员 Bot 执行 + 群聊承载多方对话**。跨机的部分由本桥的 `dual_send` 承担。

> 本插件装好后会自动注册一条名为 **`dual-bridge`** 的技能，内容是「6 个工具怎么用、按什么顺序调、有哪些坑」，并代入本机实际配置。所以模型**不用读这份手册也知道怎么跨机派活**；这份文档是给人和新机器落地用的。

### 4.1 角色映射

| ds-bot 概念 | 跨机场景里的对应 |
| --- | --- |
| Main Bot（统筹者） | 本机上的主控会话 / 主控 Bot：拆任务、分派、汇总 |
| 成员 Bot（执行者） | 对端机器上的会话：接收任务、干活、回结果 |
| 群聊 | 一个固定的「跨机任务会话」：同一台对端机器上的同一个会话，长期复用 |
| Bot-to-Bot 消息 | `dual_send`（发 + 取回复）/ `dual_inbox`（只取最新回复，不发） |

一台对端机器 = 一个（或少数几个）固定会话 = 一个「成员」。不要每次新建会话，否则对端 UI 会散成一堆会话，人也看不清上下文。

### 4.2 跨机任务分派

主控侧：

1. `dual_peers` — 确认目标对端 `在线`，拿到它的**名称**。
2. `dual_workspaces` — 列出对端工作区，挑一个跟任务相关的（比如放代码的目录），记下 workspaceId（或它的 title）。
3. **首次**对一个对端发任务：`dual_send` 带 `workspace`（新建会话，对端 UI 侧栏实时可见），拿到返回的 `sessionId` 后**写进配置的 `defaultSession`**，从此固定。
4. **后续**任务：`dual_send` 不传 `session`/`workspace`，直接用配置里的 `defaultSession` 复用同一个会话追问（`autoWorkspace` 也不会被触发，因为已经有会话了）。
5. 想先看看对端上次说了什么再决定要不要追问：用 `dual_inbox`（只读，不新建会话、不打扰对端）。
6. 长任务把 `timeoutMs` 调大（对端可能在跑构建/长脚本）。

分派模板（主控侧对模型说的话）：

```
用 dual_send 给「公司机」发任务：<任务描述>。
如果公司机已有固定会话，直接复用；没有就用 workspace <见本机配置> 建一个，并把返回的 sessionId 记下来。
```

### 4.3 方向标记约定

沿用现有约定，**由调用方写在 `message` 开头**（`dual_send` 没有 `marker` 参数，不会自动加）：

| 方向 | 标记 |
| --- | --- |
| 私人机 → 公司机 | `【私人机→公司机】` |
| 公司机 → 私人机 | `【公司机→私人机】` |

作用：两边共用同一个会话时，人和模型一眼看出这条消息是谁发的、发给谁。**别漏写** —— 漏了之后对端会话里就分不清方向了。

### 4.4 固定会话与工作区

**为什么必须固定**：

- 用 `defaultSession`（或 `session` 参数）复用会话 → 对端上是一条连续的对话，人能看到完整上下文，模型也有记忆。
- 用 `defaultWorkspace`（或 `workspace` 参数）建会话 → 会话挂到对端的工作区上，**对端 UI 侧栏实时可见**。
- `autoWorkspace: true`（默认）时，不指定工作区也会**自动挑对端「最近更新」的工作区**挂上，同样可见（`dual_send` 输出里会标注「自动选取：最近更新」）。
- 只有把 `autoWorkspace` 关掉、又没给 `workspace` 时，才会按对端 cwd 兜底建出**游离会话** —— 对端 UI 里看不到。

**规则**：

1. 每个对端至少固定一个 `defaultSession`（配置里写死）。
2. 需要「另起一条线」（新任务、新工作区）时，用 `workspace` 新建，**并把新 sessionId 补进配置**。
3. 不要自己拼 `cwd`。给对端传对端机器上不存在的路径会报 `session/create ENOENT`；要指定目录就用对端已有工作区的 workspaceId 或 title。

### 4.5 多机扩展（第三台机器起）

1. 新机器按第 1 节装插件、登同一个账号。
2. 新机器上把 `defaultPeer` 设成统筹机（或最常用的对端）；`defaultWorkspace` / `defaultSession` 指向统筹机侧那个固定会话。
3. 在**每台**已有机器的配置里按需调整 `defaultPeer`（三台机时，各机器把自己最常用的对端设为默认；其余用 `peer` 参数按名称调用）。
4. 每台机器对新对端跑一次「带 `workspace` 建会话 → 记下 `sessionId` → 写进配置」。
5. 三台以上时建议设一台为统筹机（Main），其余为执行机（成员）；统筹机负责分派与汇总，执行机之间不必互相直连（都由统筹机中转），配置更简单。

| 6 | 对端是否 online | `dual_peers` | 目标对端标 `在线` | 对端 DSH 没开 / 没登录 / 网络不通；逐项排 |
| 7 | 运行时来源是否正常 | `dual_status` 的「运行时来源」行 | 显示 `auto`（或 `own`/`host`）；若显示「已回退」且对端可达，说明宿主连接不可用、已自动切自建（这是设计行为，不是故障） | 反复回退 → 把 `runtimeMode` 显式设成 `own` |

| 11 | 方向标记是否正确 | 看消息开头 | `【本机→对端】` | 调用方漏写标记（插件不自动加）→ 在 `message` 开头补上 |
| 12 | 本机 UI 远端开关是否未被改动 | 调用 `dual_send` 前后看本机 UI | 远端选择状态无变化（零侵入） | 状态被改了 → 检查本机 `ds-harness-remote` 是否被别的插件/脚本动过；本插件从不调用 `setMode` / `selectRemoteTarget` |
| 13 | 通道是否还活着（长驻进程易撞） | 先跑一次 `dual_workspaces`（只读） | 几秒内返回；不应出现 `Noise channel is not connected`，也不应干等 60 秒后报 `RPC … timed out after 60000ms` | 出现即通道静默失效 → 0.2.1 会自动探活 + 重连 + 重试（`probeTimeoutMs` 默认 4000ms 判死）；仍频繁出现就把 `runtimeMode` 设成 `own` |

## 附：与原双向沟通的关系

本手册全程只**增加**一层封装：

- 身份、relay、登录流程仍由 `ds-harness-remote` 负责，本桥只复用：**不新建身份、不重新登录、从不调用 `setMode` / `selectRemoteTarget`**，因此不改 UI 的远端选择开关（零侵入）。本机 profile 里 `ClientModeRuntime.proxySwitch` 是 `undefined`，API 层面根本没有代理开关可被改动；收发走自建 `RemoteTypertGateway`，不经过宿主 `gatewaySwitch`。
- 原脚本 `dsh-remote-task.mjs` 与它的固定会话照旧可用，两种方式可以并存。
- 迁移时**不要删**身份目录、**不要动** `ds-harness-remote` 的配置 —— 只要这两样在，本桥装完就能用。
